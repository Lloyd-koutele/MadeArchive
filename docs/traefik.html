Traefik

Reverse proxy et load balancer cloud-native — ce document couvre ses concepts fondamentaux de façon générale, indépendamment de tout projet précis, avant une étude de cas concrète sur la façon dont MadeArchive l'utilise.

01Qu'est-ce que Traefik ?

Un reverse proxy et répartiteur de charge (HTTP/HTTPS, TCP, UDP) pensé pour les environnements conteneurisés : plutôt qu'une configuration statique à réécrire à la main à chaque changement, il peut découvrir automatiquement les services qui tournent (conteneurs Docker, pods Kubernetes…) et adapter son routage en temps réel.

Trois choses qu'il fait en une seule brique, là où on empilait traditionnellement plusieurs outils séparés :

  • Routage — décider, pour chaque requête entrante, quel service interne doit la traiter (par nom de domaine, chemin, en-tête…).
  • Terminaison TLS — gérer les certificats HTTPS, y compris leur renouvellement automatique via Let's Encrypt.
  • Répartition de charge — distribuer les requêtes entre plusieurs instances d'un même service.

02Les 4 concepts fondamentaux

Toute la configuration de Traefik s'articule autour de quatre notions, dans cet ordre de traitement d'une requête :

EntryPoints

Les ports sur lesquels Traefik écoute (ex. web = :80, websecure = :443). Le point d'entrée physique du trafic.

Routers

Une règle de correspondance (Host(...), PathPrefix(...)…) qui décide SI une requête doit être traitée, et par quel service. Une priorité départage les règles qui se chevauchent.

Middlewares

Des transformations appliquées entre le router et le service : redirection, authentification, en-têtes, limitation de débit, compression… Chaînables, dans l'ordre déclaré.

Services

La ou les adresses réelles qui traitent finalement la requête — une liste de serveurs (loadBalancer), avec sa propre stratégie de répartition.

# Exemple minimal — un router qui pointe vers un service
http:
  routers:
    mon-site:
      rule: "Host(`example.com`)"
      service: mon-service
  services:
    mon-service:
      loadBalancer:
        servers:
          - url: "http://127.0.0.1:8080"

Avec un middleware d'authentification enchaîné :

http:
  routers:
    admin:
      rule: "PathPrefix(`/admin`)"
      middlewares:
        - auth-basique
      service: mon-service
  middlewares:
    auth-basique:
      basicAuth:
        users:
          - "utilisateur:motdepassehashé"

03Configuration statique vs dynamique

Une distinction qui prête souvent à confusion, mais essentielle :

Configuration statique

Définie au démarrage de Traefik (fichier traefik.yml, ou arguments en ligne de commande) — ne peut pas changer sans redémarrer le conteneur. Ce sont les entryPoints, les providers activés, les résolveurs de certificats.

Configuration dynamique

Les routers, services et middlewares eux-mêmes — rechargée à chaud, sans interruption de service, sans redémarrer Traefik. Fournie par un ou plusieurs providers (voir plus bas) : un fichier surveillé, ou l'API Docker/Kubernetes interrogée en continu.

04Providers — d'où vient la configuration dynamique

À savoir Plusieurs providers peuvent tourner en même temps — Traefik fusionne leurs configurations. Le provider docker exige un accès (lecture seule, idéalement) au socket Docker, ce qui n'est pas anodin en termes de surface de sécurité ; le provider file n'y touche jamais.

05TLS & Let's Encrypt

Traefik peut obtenir et renouveler automatiquement des certificats via Let's Encrypt (protocole ACME), sans intervention manuelle. Trois façons de prouver qu'on contrôle le domaine :

  • HTTP-01 — le plus simple : Let's Encrypt vérifie un fichier accessible sur le port 80 du domaine. Ne fonctionne pas derrière certains load balancers en amont, ni pour un certificat wildcard.
  • DNS-01 — Traefik crée un enregistrement DNS temporaire (nécessite les identifiants API du fournisseur DNS). Seule méthode permettant un certificat wildcard, et fonctionne même si le port 80 n'est pas joignable publiquement.
  • TLS-ALPN-01 — validation directement sur le port 443, sans passer par le port 80 ni le DNS.

Pour un usage interne ou de développement (pas de domaine public), un certificat auto-signé ou généré par un outil comme mkcert peut être déclaré statiquement, sans passer par ACME du tout.

06Répartition de charge, sessions collantes & santé des serveurs

Par défaut, un service avec plusieurs servers répartit les requêtes en tourniquet (round robin, avec pondération possible). Deux réglages courants viennent affiner ce comportement :

http:
  services:
    mon-service:
      loadBalancer:
        sticky:
          cookie:
            name: srv_id
        servers:
          - url: "http://10.0.1.10:8080"
          - url: "http://10.0.1.11:8080"
        healthCheck:
          path: /healthz
          interval: 5s
          timeout: 2s
  • sticky (sessions collantes) — un cookie posé à la première réponse fixe quel serveur traite les requêtes suivantes DU MÊME client. Utile quand un service garde un état en mémoire propre à chaque instance (voir l'étude de cas plus bas).
  • healthCheck — Traefik interroge périodiquement chaque serveur ; celui qui ne répond plus est automatiquement retiré de la rotation (et le cookie sticky réattribué si besoin) jusqu'à ce qu'il redevienne sain.

07Dashboard & API

Traefik expose un tableau de bord web (et l'API JSON qui l'alimente) montrant en direct tous les routers, services et middlewares actifs — pratique pour diagnostiquer un routage qui ne se comporte pas comme prévu.

Sécurité Ce tableau de bord expose l'intégralité de la configuration, potentiellement des informations sensibles. Ne jamais l'exposer publiquement sans authentification — le sécuriser par un middleware (authentification simple, liste d'IP autorisées) via un router dédié pointant vers le service interne api@internal, jamais en accès direct.

08Étude de cas : comment MadeArchive l'utilise

Application concrète des concepts ci-dessus, dans ce projet précis :

Image & initialisation

Image maison (pas l'image officielle telle quelle) : un point d'entrée personnalisé régénère le fichier de configuration dynamique depuis un gabarit à chaque démarrage, en y substituant le domaine réel lu depuis .env — une seule source pour cette valeur, là où deux copies manuelles désynchronisables existaient avant.

Provider choisi : file, pas docker

Le provider docker a été essayé et abandonné (incompatibilité constatée avec Docker Desktop en développement) — jamais retesté sur un vrai hôte Linux de production. Le provider file actuel fonctionne, mais sa configuration reste statique : Traefik n'a plus besoin du socket Docker, en échange d'une topologie à éditer à la main.

Routage & TLS

Un seul domaine public, routage par chemin — /api/* vers le backend, tout le reste vers le frontend. Certificat mkcert en développement (sélectionné par SNI), Let's Encrypt (HTTP-01) dès qu'un vrai domaine public est configuré, sans changer de fichier.

09Mise à l'échelle : une piste de plus

Dans la documentation de MadeArchive, le blocage identifié pour faire tourner plusieurs instances de l'API était OcrSessionCache — les sessions d'archivage (aperçu → finalisation) vivent en mémoire du process Java, propres à chaque instance. La solution envisagée était de migrer ce cache vers Redis (déjà présent dans la stack).

Piste alternative, plus simple Les sessions collantes (sticky, voir section 6) résoudraient le même problème sans toucher au code Java : si le client qui a fait la Phase 1 est systématiquement renvoyé vers la même instance pour la Phase 2, la session en mémoire reste toujours disponible là où elle a été créée. Moins robuste qu'un cache partagé (si CETTE instance redémarre entre les deux phases, la session est perdue quand même), mais une configuration Traefik suffit à la mettre en place — à comparer selon l'effort acceptable pour chaque option.
